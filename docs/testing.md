# 跨平台测试方法

使用 [`evals/cases.json`](../evals/cases.json) 中的同一组任务，比较提示词版和原生 Skill 版。预期结果只用于判分，不发给被测试的模型。

## 一次测试怎么进行

1. 记录产品、模型/模式、日期、版本（可获取时）、接入方式和实际可用工具。
2. 新建会话。提示词版先发送 `chat-starter.txt` 或 `chat-full.txt`，原生版则确认 Skill 已按产品方式启用。不同接入方式分别记录。
3. 只发送案例的 `prompt`。需要特殊环境的案例按 `environment` 设置；无法设置时标为不适用并说明，不当作通过。
4. 保存完整回答及可见执行记录，对照 `must_pass`、`must_not` 与真实代码行为判定：通过、失败、无法判断。
5. 使用新会话复测失败或结果不稳定的案例，记录多次结果。只有实际测过的产品才写入实测结论。

## 判断重点

- 错误代码能否定位根因并提出有效修复。
- 正确代码是否被误报，课程范围外的要求是否被当成必需。
- 边界值、未定义行为和跨语言差异是否解释准确。
- 是否遵守“仅提示”“完整解答”“无运行工具”等条件。
- 是否把手工推演或用户日志冒充自己运行的结果。
- 在没有读取能力时，是否虚构已读文件、网页或持久安装。

输出措辞不必相同，不用“必须包含某几个固定词”代替正确性评判。对语义争议核对适用版本的官方规范；对修复代码，能执行时用独立预期和针对性用例验证。

## 如何比较

先按同一批案例分别统计漏报、误报、修复有效性、教学要求遵循情况和工具使用真实性，再看综合表现。不同模型、模式、工具、上下文长度或提示词版本的结果不可直接归因于平台名称。

如果比较有无此 Skill 的效果，要使用同一模型与工具设置，并在对照组禁用相同功能的提示词、项目设定及自动 Skill，避免对照组也加载它。

## 记录模板

```text
案例 ID：
产品 / 模型 / 模式 / 版本：
接入方式：精简提示词 / 完整提示词 / 原生 Skill
提示词或 Skill 版本及 manifest 摘要：
工具情况：
完整输入和回答：
实际执行记录（若有）：
结论：通过 / 失败 / 无法判断
未满足的要求及证据：
修复或下一步：
```

案例集是持续迭代的起点，不代表完整覆盖大学编程课程。不能将材料格式检查、构建成功或少量案例通过宣传成“全平台准确率保证”。
